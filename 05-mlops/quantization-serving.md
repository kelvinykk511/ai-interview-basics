# 量化 Serving：GPTQ／AWQ／FP8（上線視角）

## 人話

同一套權重用 **FP16／BF16** 跑最「原汁原味」，但顯存與帶寬貴。**量化**把權重（有時連啟動值）收成更少 bit，讓同卡塞更大模型或更高併發。面試別背論文細節，要講清：**權重量化 vs KV／啟動量化**、**離線標定（GPTQ／AWQ）vs 訓練感知／硬體原生 FP8**、以及「省了顯存卻可能傷品質或某些 op 變慢」的取捨。後端類比：像把熱數據從「完整對象」改成「緊湊編碼 + 反序列化成本」——容量換 CPU／精度。

## 面試短答

- **目標**：降權重顯存、有時降記憶體帶寬瓶頸 → 更大模型／更高 batch；不一定自動降延遲（看 kernel 是否真的走量化路徑）。
- **GPTQ**：離線、**逐層／分塊**用校準數據做權重 int 量化（常見 4-bit），最小化輸出重建誤差；部署載入量化 checkpoint。適合「已經 fine-tune 完、要壓進卡」。
- **AWQ**：也偏權重量化；核心直覺是**保護對輸出影響大的通道**（activation-aware），少用或不用大量重訓練。實務常與 GPTQ 並列為「4-bit 權重上線」選項，比誰在你的模型＋硬體上更快／更準。
- **FP8**：更偏**硬體友好**的 8-bit 浮點（Hopper／近期推理棧常見）；可覆蓋權重與部分啟動，走專用 tensor core。和「純 int4 權重 + FP16 啟動」路徑不同。
- **別混**：權重 4-bit ≠ KV cache 也 4-bit。KV／啟動量化是另一刀，省的是**併發與長 context 的動態顯存**，對品質更敏感。
- **風險**：困惑度／任務指標掉點；長尾任務（數字、代碼、工具 JSON）更脆；某些層／形狀 fallback 到慢路徑 → 吞吐反而差；校準集和線上分布不一致。
- 後端類比：GPTQ／AWQ ≈ 離線壓縮構建產物；FP8 ≈ 換用支援更好的指令集／dtype；要回歸測試，不是只看「顯存少一半」。

## 常見追問（含答案）

**Q：為什麼量化後顯存少了，TTFT 卻沒變好、甚至更差？**  
A：若瓶頸在 **prefill 算力** 或 kernel 未優化（反量化開銷、不支援的 shape 走 fallback），權重變小不保證更快。要看 profiler：是否真的跑量化 gemm、GPU util／bandwidth、以及 batch 是否因省顯存而加大卻拖高排隊。

**Q：GPTQ 和 AWQ 面試怎麼一句分？**  
A：都是**離線權重量化**常見方案。GPTQ 偏「用校準統計把量化誤差壓到層輸出」；AWQ 偏「依啟動特徵保護重要通道」。選型用**你的模型 + 目標硬體 + 業務評測集**比品質與速度，不要背「誰絕對更好」。

**Q：FP8 和 INT4 怎麼選？**  
A：INT4 權重通常**更省顯存**，適合把 70B 級塞進較少卡；品質與 kernel 成熟度要驗證。FP8 常在新硬體上**吞吐／延遲更甜**，精度通常比 4-bit 權重溫和，但顯存收益小於 4-bit。也可「權重 INT4 + 啟動／KV 更高精度」混合。

**Q：上線前最少做哪些驗證？**  
A：1）業務 golden set（含工具 JSON／數字／多語）對比 FP16 baseline；2）長 context 與高併發下的 TTFT／TPOT／OOM；3）A/B 或 shadow（見 [online eval](../07-system-design/online-llm-eval-canary.md)）；4）確認serving 框架對該量化格式的正式支援與版本釘選。

## 小練習

**題：** 團隊要把 70B 客服模型從 2×A100 80GB（FP16 權重勉強＋低併發）壓到單卡或同卡更高 QPS。有人提 AWQ-4bit，有人提 FP8。你會怎麼決策？列出決策步驟與兩個「否決項」。

**參考答案：**  
1. **步驟**：確認硬體是否吃香 FP8；用同一份線上抽樣＋golden（含 function call JSON）比 FP16 vs AWQ-4bit vs FP8 的任務分數；在目標併發下壓測 TTFT／TPOT／顯存／否決 OOM；檢查 serving 棧對格式的支援與回滾開關。  
2. **否決項**：工具呼叫／結構化輸出正確率相對 FP16 掉超過約定門檻；或量化 kernel fallback 導致 P99 比現況更差（省了卡卻換不來穩定延遲）。  
3. **補充**：若只是「塞得下」優先 INT4；若卡已支援且品質敏感，可先 FP8；KV 仍吃緊再單獨評估 KV 量化，不要與權重一把抓。
