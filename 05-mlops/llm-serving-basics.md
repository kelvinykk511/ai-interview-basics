# LLM Serving：延遲、吞吐與 KV Cache

## 人話

把模型跑起來，不像開一個普通 Java API。推理是「算力很重、記憶體很吃」的服務：你要在**首字延遲（用戶多久開始看到字）**和**整體吞吐（同一張 GPU 一秒能服務多少請求）**之間做取捨。關鍵黑盒是 **KV Cache**——模型邊生成邊把中間狀態存下來，避免每一步從頭算。

## 面試短答

- **TTFT（Time To First Token）**：從請求進到第一個 token 出來。用戶體感「有沒有在動」多半看這個。
- **TPOT / inter-token latency**：之後每個 token 的間隔；影響「讀起來順不順」。
- **Throughput**：GPU 單位時間完成多少 token / 多少請求。產線常優化吞吐，聊天產品常盯 P99 TTFT。
- **Continuous batching（連續批處理）**：不是等一組請求湊齊才跑，而是每步動態把新請求塞進正在跑的 batch（像網關動態加連接），提高 GPU 利用率。
- **KV Cache**：每個請求、每個層的 Key/Value 狀態；序列越長、並發越高，顯存越吃。顯存不夠 → 拒收、換出、或降併發。
- 和後端類比：TTFT ≈ 首包延遲；batching ≈ 把小請求合成批；KV Cache ≈ 連線／session 狀態佔記憶體。

## 常見追問（含答案）

**Q：為什麼「提高 batch size」不一定讓用戶更快？**  
A：吞吐通常上升，但單請求可能要等更久才進 batch，或同一步要算更多序列 → TTFT / P99 變差。聊天要控延遲，離線摘要／評分可以偏吞吐。

**Q：長 context 為什麼貴又慢？**  
A：Attention 與 KV Cache 大致隨序列長度變重；prompt 很長時 prefill（算完 prompt、填好 KV）本身就很重，TTFT 會爆。實務會截斷、摘要、RAG 只塞相關片段、或 prompt cache。

**Q：自建推理 vs 調 API 怎麼選？**  
A：API：快上線、彈性、少運維，但單價、限流、數據出境要談。自建：可控延遲／隔離／成本曲線，但要扛 GPU、調度、版本、監控。面試可講「流量穩定＋敏感數據／要抠成本再自建」。

## 小練習

**題：** 線上客服 bot，P99 TTFT 突然從 400ms 變成 2s，吞吐卻差不多。你會先查哪三件事？  

**參考答案：**  
1. 併發／隊列：是否排隊變長（限流、worker 數、上游超時重試風暴）。  
2. Prefill 變重：平均 prompt 長度、RAG top-k／chunk 是否變大、系統 prompt 膨脹。  
3. KV／顯存壓力：是否觸發換出、降 batch、或 GPU 被別的模型／任務佔用；同時看是否有少數超長請求拖垮調度。
