# Prompt Caching 與推理成本

## 人話

LLM 計費／耗時大致跟「送進去多少 token＋吐出多少 token」有關。系統提示、工具定義、RAG 常重複塞同一大段——**Prompt cache** 就是讓服務端記住「這段 prompt 前綴已經算過／可復用」，少付重複 prefill 的錢與時間。像 CDN／本地快取：熱的前綴命中就便宜，冷的或每次都改就命不中。

## 面試短答

- **成本拆分**：input tokens（常含巨大系統提示＋檢索）＋ output tokens（通常更貴）。RAG 把 top-k 片段塞進 prompt → input 成本易爆。
- **Prompt caching**：穩定、較長的**前綴**（系統指令、工具 schema、固定知識）可被快取；後綴（用戶問題、每次不同的檢索結果）仍每次算。
- **命中條件（概念）**：前綴要穩定、夠長、請求間重複；前綴任意 byte 級改動常導致 miss。供應商細節不同，面試講「穩定前綴＋變動放後面」。
- **和 KV cache 的關係**：Serving 的 KV cache 是單次生成過程中的狀態；prompt cache 偏跨請求復用已算過的前綴（產品／計費層）。別混成同一個東西，但都在省 prefill。
- **省錢手段**：縮短／摘要檢索、降 top-k、小模型做路由／改寫、輸出 max tokens、快取熱問答、批次離線任務、選對價位模型。
- 後端類比：穩定前綴 ≈ 可 CDN 的靜態頭；每次不同的 RAG 片段 ≈ 不可快取的動態 body。

## 常見追問（含答案）

**Q：為什麼「把動態的 RAG 片段放在 prompt 最前面」常更貴？**  
A：快取多半綁**前綴**。動態內容靠前 → 前綴每次變 → cache miss → 整段重算 prefill。正確姿勢：固定系統／工具在前，變動的檢索與用戶問題在後。

**Q：Cache 命中率低怎麼辦？**  
A：檢查前綴是否被時間戳、隨機 ID、每次重排的工具列表弄碎；統一模板；合併多租戶仍可共享的系統段；對「完全相同的熱門問題」做應用層回應快取（比 prompt cache 更狠）。

**Q：只靠 cache 夠不夠控成本？**  
A：不夠。還要：檢索別塞無關長文、輸出長度上限、便宜模型做分類／拒答、貴模型只接手難題、監控 input/output tokens per request 與 P95。Cache 是「重複前綴」優化，不是架構免死金牌。

**Q：自建推理有「prompt cache」嗎？**  
A：自建常透過前綴共享 KV、radix／block 管理（視引擎）復用相同 prefix 的計算；概念類似，但是你自己管顯存與調度，不是雲帳單上的那一行。面試可對齊：「目標都是少做重複 prefill」。

## 小練習

**題：** 內部助手：系統提示 8k tokens（含工具定義），每次再塞 6 段 RAG（約 4k），用戶問題很短。日呼 50 萬次，很多請求系統段完全一樣。怎麼降成本又不重傷品質？  

**參考答案：**  
1. **穩定前綴＋prompt cache**：系統＋工具固定放最前，開啟／確認供應商 cache；禁止每次改動前綴。  
2. **動態段後置並瘦身**：RAG 放後；降 top-k、切短 chunk、必要時先 rerank 再只塞 2–3 段；監控平均 input tokens。  
3. **分層**：熱門 FAQ／完全命中文檔用快取答案或小模型；難題才走大模型；設 output cap。用 golden set 確認瘦身後忠实度不掉再全量。
