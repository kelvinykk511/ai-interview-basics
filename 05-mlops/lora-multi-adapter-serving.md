# LoRA／多 Adapter Serving：一底多租戶

## 人話

全量微調（full SFT）會為每個產品／租戶複製一整份模型權重——顯存與發布成本像「每個租戶一台專屬 JVM」。**LoRA（Low-Rank Adaptation）**在**凍結的底座模型**上只訓練很小的低秩增量（adapter）；上線時底座只載一份，按請求掛上對應 adapter。後端類比：**共用 JVM／核心服務 + 每租戶 plugin／feature flag**——核心不變，差異化邏輯熱插拔。

## 面試短答

- **LoRA 是什麼**：在注意力／MLP 等線性層旁掛 \(W' = W + BA\)（\(B,A\) 低秩）；訓練時只更新 adapter，底座權重凍結。推理時可 merge 進底座，或**動態掛載**保持底座共享。
- **為什麼 CEX／後端在意**：風控話術、客服、合規摘要、多產品 bot 往往要「同一底座能力 + 不同行為／語料」。Full fine-tune × N 租戶 = 顯存與鏡像爆炸；多個小 adapter（數 MB～百 MB 級）可共卡。
- **Serving 模式**：  
  1. **請求路由 adapter id**（header／租戶配置）→ 引擎載入／切換該 adapter；  
  2. **熱插拔（hot-swap）**：底座常駐，adapter 按需 load／unload；  
  3. **Merge 後當獨立模型**：延遲簡單但失去共享，適合流量極大且穩定的單租戶。
- **記憶體賬**：底座權重 + KV 仍是大頭；adapter 增量相對小。瓶頸常在「同時常駐幾個 adapter + 各請求 KV」，不是 adapter 本身。
- **Full SFT vs LoRA**：領域大改、要動知識邊界、或品質卡在 LoRA 天花板 → 考慮 full／較大 PEFT；多租戶風格／術語／拒答策略差異 → LoRA 通常夠用且運維友好。
- **坑**：adapter 與底座**版本必須釘死**（換底座≠舊 adapter 可掛）；錯掛 adapter = 錯租戶行為；切換若觸發冷載入會抖延遲；rank／目標模組影響品質與顯存。
- 後端類比：底座 ≈ 共用 JVM；adapter ≈ 租戶 plugin；adapter id 路由 ≈ 網關按 `tenantId` 選策略；版本釘選 ≈ 依賴座標不可漂。

## 常見追問（含答案）

**Q：為什麼「一個底座 + 很多 LoRA」比「每個租戶一份全量權重」省？**  
A：全量權重是幾十 GB 級複製；LoRA 只存低秩增量，體積小幾個數量級。Serving 時 GPU 上**底座只載一次**，多租戶請求共用底座計算圖，差在套哪組 adapter。像一台機器跑一個 JDK，classpath 掛不同插件，而不是每租戶一個完整 JDK 副本。

**Q：請求級切換 adapter，延遲會不會炸？怎麼設計？**  
A：冷切換（磁碟→GPU）會抖。實務：熱門 adapter **常駐**、冷門 LRU；批次內盡量同 adapter 聚類（減少 thrash）；或 merge 高 QPS 租戶成獨立 replica。監控 **adapter miss／load 次數、切換 P99、每 adapter QPS**。面試講「路由便宜、載入貴——要有快取與親和」。

**Q：LoRA 什麼時候不夠，要上 full SFT 或更大方案？**  
A：要改的行為遠超「風格／術語／少量任務頭」、安全對齊要重做、或評測顯示 LoRA 怎麼加 rank 都追不上全量。也要看資料量與合規：有些場景必須獨立權重隔離（租戶要求模型檔物理分離），那時共享底座在合規上就不行，只能分部署。

**Q：多租戶錯掛 adapter 或底座升級沒釘版本，事故長什麼樣？**  
A：A 租戶講到 B 租戶話術／拒答策略失效／幻覺領域知識錯位——屬**正確性與合規事故**，不是單純延遲。防護：adapter 產物寫死 `base_model_id + commit/hash`；閘道校驗租戶→adapter 映射；金絲雀先掛 shadow；底座升級走「新底座 + 重訓／重驗證 adapter」流水線，禁止默默互換。

## 小練習

**題：** 交易所要上三條助手：零售客服、機構 API 支援、內部合規問答。共用同一個 70B 底座。你會怎麼切 LoRA／部署拓撲？列出至少三個你會釘死的運維約束，以及一個「寧可 full／獨立副本」的條件。

**參考答案：**  
1. **切分**：三條各一個（或一組）LoRA；閘道按產品線／內部角色路由 `adapter_id`；敏感合規可再加獨立安全策略層，不混在客服 adapter。  
2. **拓撲**：一組 GPU 常駐底座 + 熱門三個 adapter；流量差很大時，QPS 最高那條可 merge 成獨立 replica，其餘動態掛載。  
3. **運維約束**：底座與 adapter **版本座標釘死**；租戶／產品→adapter 映射走配置中心＋審計；切換與載入納入 SLI（load 次數、錯誤掛載告警）；評測集按產品線分開回歸。  
4. **寧可獨立**：合規線要求權重物理隔離或資料不能進共享顯存調度、或評測證明 LoRA 無法達標 → 合規線獨立 full／獨立部署，另兩條繼續共享底座。
