# LLM Gateway：限流、熔斷與冪等重試

## 人話

把 LLM 當依賴時，你不會讓每個微服務直連 OpenAI／自建推理叢集——中間通常有一個 **LLM Gateway**（像 API Gateway + 客戶端庫）。它負責：選模型、加 API key、限流、超時、重試、熔斷、記帳、以及把錯誤翻譯成你自家的錯誤碼。面試重點不是「會不會設 rate limit」，而是：**哪些失敗可重試、重試會不會重複扣費／重複副作用、以及上游抖動時怎麼保護自己的服務**。

## 面試短答

- **Gateway 職責**：統一入口、認證、路由（cheap vs strong model）、quota、觀測、策略（timeout／retry／fallback）。業務服務只認自家 SDK／proto。
- **限流（rate limit）**：分層——每用戶／每租戶／全域／每模型。算法常見 token bucket／leaky bucket。LLM 還要按 **RPM（請求）與 TPM（token）** 兩維；長 prompt 吃 TPM 很快。超限回 429 + `Retry-After`，客戶端要可讀。
- **熔斷（circuit breaker）**：上游錯誤率／延遲超閾 → Open（快速失敗）→ Half-Open（放少量探針）→ Closed。避免全站線程卡在等 GPU。可對「供應商 A」與「模型 B」分開熔斷。
- **重試原則**：只重試**冪等且可判定為暫時性**的失敗（連線重置、502/503、部分 429）。**不要**盲目重試已開始產生副作用的請求（已寫 DB、已觸發工具、已扣費不明）。
- **冪等鍵**：客戶端帶 `Idempotency-Key`（或 `request_id`）；Gateway 在成功／進行中窗口內對同 key 去重或回放同一結果。像支付回調、Kafka producer idempotent。
- **Fallback**：主模型熔斷 → 備援模型／緩存／規則默認；要標 `degraded=true`，別假裝同品質。
- 後端類比：限流 ≈ 網關 QPS；熔斷 ≈ Hystrix／Resilience4j；冪等鍵 ≈ 支付 idempotency-key；TPM ≈ 按 payload 大小計費的配額。

## 常見追問（含答案）

**Q：429 和 503 重試策略有何不同？**  
A：429 多半是配額——尊重 `Retry-After`／指數退避 + jitter，並考慮降級到更小模型或排隊。503／連線錯誤是暫時不可用——退避重試，但次數要少（例如 2–3），並把負載從壞實例摘掉。兩者都要有**總 deadline**（整條業務只願等 3s），避免重試把尾延遲打爆。

**Q：流式（SSE）請求怎麼重試？**  
A：一旦已向用戶推過 token，**不能**靜默重開同一個 stream 當「同一請求」——用戶會看到重複或跳躍。實務：首包前（未 commit 任何 delta）可重試；首包後只允許明確的「重新生成」或斷線產品流程。取消與重試都要綁 `request_id`。

**Q：為何「超時就重試」很危險？**  
A：你的客戶端超時了，上游可能仍在算並計費，甚至 tool 已執行。重試會造成**雙重扣費／雙重副作用**。正確做法：超時時盡力 cancel 上游；寫操作必須冪等；讀取可重試；對「不確定是否成功」走查詢狀態或用 idempotency 回放，而不是再打一槍。

**Q：多租戶下如何設計限流才公平？**  
A：每租戶獨立 bucket + 全局限額防一家打爆；大客戶可買更高配额。重要路徑（登錄風控）與批量（離線摘要）分開隊列與配額。監控「被限流次數／租戶」避免靜默餓死小租戶。

## 小練習

**題：** 交易風控服務同步調 LLM 分類可疑提現。供應商偶發 502，有人建議「超時 2s，失敗自動重試 5 次」。指出三個風險，並給一版可上線的策略。  

**參考答案：**  
1. **重試放大尾延遲與費用**：5 次 × 長 prompt 可能拖垮線程池並雙重計費。  
2. **超時後上游仍在跑**：不 cancel 就重試 → 重複推理；若將來接 tool 更可怕。  
3. **風控路徑要可降級**：一直重試不如快速 fallback 到規則引擎 `review`。  
可上線策略：總 deadline 例如 800ms–1.5s；僅對連線錯誤／502 **最多 1 次**重試且帶 jitter；一律帶 `Idempotency-Key`；超時必須 abort；熔斷錯誤率；失敗默認 `review` + 異步再分析；指標看 `llm_timeout`、`retry_count`、`fallback_rule`、成本。
