# LLM 成本路由／模型級聯

## 人話

唔係每條請求都要用最貴嘅大模型。好似客服分流：簡單嘢畀細模型，難嘅先轉大模型。目標係質量唔跌嘅前提下，壓低平均成本同延遲。

三種做法：

- **前置路由（router）**：請求入嚟先分類（規則、細分類模型、embedding 近鄰），決定去邊個模型。快，但分錯就錯。
- **級聯（cascade）**：先用細模型答，再用驗證器判斷夠唔夠好，唔夠先升級去大模型。質量穩，但升級嗰批付兩次錢、延遲疊加。
- **混合**：明顯難嘅 router 直接送大模型，中間地帶先 cascade。

**成本公式**：cascade 平均成本 = `c_small + p_escalate × c_large`。例：`c_small=1`、`c_large=10`、升級率 30% → 1+3=4，比全部大模型（10）省 60%。但升級率去到 90% → 1+9=10，同直接用大模型一樣貴，仲慢咗 —— 所以**升級率係核心監控指標**。

## 面試短答

先建離線 eval 集，畫 cost–quality Pareto；router 按任務類型／難度分流，邊界請求用 cascade + 驗證器升級；監控升級率、每請求成本、p95 延遲同質量 KPI；加 semantic cache 同 prompt caching；provider 故障有 fallback 鏈 + circuit breaker。

## 常見追問（含答案）

**Q1：驗證器點揀？**  
A：結構化任務用確定性檢查最可靠（JSON schema、SQL 能 parse／執行、單元測試）；開放式用細 judge 或 self-consistency（抽幾次睇一唔一致）。模型自報信心唔可靠，要用 eval 集畫 confidence vs accuracy 校準，再揀閾值。logprob 唔係每個 API 都畀。

**Q2：Router 點訓練同評估？**  
A：用歷史流量兩個模型都跑，用 judge／人工標「細模型夠唔夠」做二分類 label；評估睇「達到目標質量時大模型調用比例」；流量分佈同模型版本會變，要定期重訓同重校閾值。

**Q3：Semantic cache 有咩坑？**  
A：相似唔等於相同 —— 「轉 100 去 A」同「轉 1000 去 A」embedding 好近但答案唔同；要將數字／實體做 exact-match key、按租戶同權限隔離、設 TTL、個人化或時效性內容唔 cache，相似度閾值用 eval 定。

**Q4：Provider 掛咗或限流？**  
A：fallback 鏈去同級別另一 provider（prompt 兩邊都要測過）；circuit breaker；429 重試加 jitter；按租戶做 token 預算限流；降級去細模型要打標記方便事後分析。

**Q5：點證明省錢冇犧牲質量？**  
A：A／B 或 shadow 比較線上質量（解決率、讚踩、人工抽檢）+ 每請求成本 + p95 延遲，而且要按 segment 睇，唔好淨睇平均 —— 某一類難題可能大跌但被平均數遮住。

## 小練習

**題：** 客服 bot 每日 100 萬請求，全用大模型每次 $0.01；細模型每次 $0.001，離線 eval 顯示細模型對 70% 請求達標。(a) 驗證器完美嘅話 cascade 每日幾錢？(b) 驗證器將 5% 嘅錯答放行會點？(c) 點改？

**參考答案：**

(a) 全部先過細模型 $1,000；30% 升級 = 30 萬 × $0.01 = $3,000；合共 $4,000／日，對比 $10,000 省 60%。代價係嗰 30% 延遲 = 細模型 + 驗證 + 大模型。

(b) 30 萬個錯答 × 5% = 1.5 萬個錯答去到用戶，即總流量 1.5% 質量下降。

(c) 收緊閾值（升級多啲、成本升）；高風險類別（退款、帳戶、金額）router 直送大模型；盡量用確定性檢查；明顯難嘅請求跳過細模型避免延遲超 SLO；上線後持續抽檢放行樣本。
