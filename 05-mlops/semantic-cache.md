# Semantic Cache：LLM 回應快取（命中、誤命中與失效）

## 人話

普通快取是「key 一模一樣才命中」。用戶問 LLM 的問題，字面幾乎每次都唔同（「點樣改密碼？」vs「密碼要點改」），所以 exact-match 命中率好低。**Semantic cache** 做法：把問題轉成 embedding，去向量庫搵「意思最近」的舊問題；相似度過門檻就直接回舊答案，**完全跳過 LLM**（省錢、延遲由幾秒變幾十毫秒）。

代價：佢係「近似命中」。兩條問題向量好近，但答案可以完全唔同——「點樣**開**通 2FA」vs「點樣**關**閉 2FA」、「BTC 提幣手續費」vs「ETH 提幣手續費」。誤命中＝自信地答錯，比慢更差。所以重點唔係「點樣做」，而係**幾時唔應該命中**。

後端類比：exact cache ≈ Redis `GET key`；semantic cache ≈ 用 ANN 做「模糊 key 查找」，key 有碰撞風險，所以要加 namespace、門檻同驗證。

## 面試短答

- **分層**：L1 exact-match（正規化後 hash：trim、大小寫、全半形）→ L2 semantic（embedding + ANN，top-1 相似度 ≥ 閾值）→ miss 才打 LLM，回寫快取。
- **Cache key 唔只係問題**：要把會改變答案的維度放入 **namespace / 硬過濾**：tenant、語言、用戶權限／角色、模型版本、system prompt 版本、RAG 知識庫版本、工具可用性。向量相似只喺同一 namespace 入面比。
- **閾值係 precision/recall 取捨**：用標註過的「應命中／唔應命中」問題對調閾值，**按 precision 定**（例如誤命中 ≤ 0.5%），唔好按命中率定。不同意圖可以不同閾值。
- **邊個可以 cache**：通用、無個人化、無實時數據的問答（FAQ、文檔解釋）。**唔好 cache**：含用戶私人數據、餘額／價格／訂單狀態等實時內容、tool call 有副作用的回應、多輪對話中依賴上文的問題（「咁第二個呢？」）。
- **失效**：TTL＋事件驅動失效（文檔更新／prompt 改版／換模型 → bump 版本號，舊 namespace 自然作廢）。同 RAG freshness 一樣：答案引用的文檔變咗，快取答案就係髒數據。
- **度量**：命中率、**誤命中率**（抽樣人工／LLM-judge 覆核）、節省成本、命中路徑 P95、用戶負反饋（👎）喺命中 vs 非命中的差異。

## 常見追問（含答案）

**Q：同 prompt caching / prefix KV cache 有咩分別？**  
A：Prompt cache／prefix KV 係**省 prefill 計算**，模型仍然會生成，答案係新鮮的，零正確性風險。Semantic cache 係**直接返回舊答案**，連 decode 都慳埋，但有誤命中風險。三者可疊加：semantic miss 後打 LLM，prompt 前綴仍可命中 prompt cache。

**Q：多輪對話點用 semantic cache？**  
A：只用最後一句做 key 好危險（「咁 ETH 呢？」脫離上文冇意義）。做法：①只對**第一輪**或「自足問題」啟用；②或者先用小模型把問題**改寫成獨立問題**（query rewrite）再做 key；③偵測代詞／省略就直接 bypass。寧願少命中都唔好答錯上文。

**Q：「開通 2FA」同「關閉 2FA」相似度 0.95，點防？**  
A：Embedding 對否定、反義、數字、實體（幣種、金額）唔敏感。多層防護：①相似度閾值之上再加 **cross-encoder / 小模型驗證**「兩條問題答案是否可互換」；②抽取關鍵實體（幣種、動作、數字）做**硬匹配**，唔一致就 miss；③高風險意圖（資金、安全設置）直接唔走 semantic cache。

**Q：快取污染點處理？**  
A：LLM 一次答錯／幻覺被寫入快取，之後被放大成千上萬次。對策：只回寫「有好信號」的答案（通過 grounding 檢查、冇 👎、或經人工審核的 FAQ 種子）；快取條目記錄來源請求、模型版本、引用文檔 ID，方便按文檔或版本批量刪除；被 👎 的命中條目自動下架。

**Q：多租戶點樣防數據外洩？**  
A：tenant_id 係**硬過濾／獨立 collection**，唔係靠相似度「應該唔會撞」。否則 A 公司的內部答案會命中 B 公司的相似問題——等同跨租戶洩漏。含 PII 的回應根本唔寫入共享快取。

**Q：命中率幾多先值得做？**  
A：計數：成本節省 ≈ 命中率 × 單次 LLM 成本 − (embedding + ANN + 驗證成本)。客服 FAQ 類流量長尾集中，可以有幾十 % 命中；開放式創作／代碼助手命中率好低，做咗反而加延遲（miss 路徑多咗 embedding + 查詢幾十 ms）。先用離線日誌重放估命中率同誤命中率再決定。

## 小練習

**題：** 交易所客服機器人，日 200 萬次提問，老闆要你加 semantic cache 慳 LLM 成本。列出設計要點，以及你會**排除**哪些問題。

**參考答案：**
1. **分層**：正規化 exact-match → semantic（同 namespace：tenant/語言/KB 版本/prompt 版本/模型版本）→ LLM。
2. **排除**：涉及用戶本人數據（我張單、我餘額、我 KYC 狀態）、實時數據（費率、價格、維護狀態——或者只 cache 模板、實時值即時填）、多輪依賴上文的追問、有副作用的工具調用、安全／資金類高風險意圖。用意圖分類器做 gate。
3. **防誤命中**：閾值按標註集 precision 調；實體硬匹配（幣種、鏈、動作開／關）；邊界分數段加 cross-encoder 驗證。
4. **新鮮度**：TTL + 公告／幫助中心文章更新時 bump KB 版本；條目記錄引用文檔 ID 支持精準失效。
5. **防污染**：只回寫通過 grounding 檢查的答案，或以人工審核 FAQ 做種子；👎 自動下架。
6. **上線**：先離線用歷史日誌重放估命中率／誤命中率；再 shadow mode（算命中但唔返回，對比 LLM 答案）；最後小流量灰度，監控誤命中率、👎 率、成本同 P95。
