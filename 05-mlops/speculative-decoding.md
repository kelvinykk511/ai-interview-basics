# Speculative Decoding：草稿模型加速推理

## 人話

LLM 生成是**一步一個 token**，GPU 很多時間在等記憶體，算力沒吃滿。**投機解碼（speculative decoding）**的做法是：用一個**小而快的草稿模型（draft）**先猜接下來幾個 token，再讓**大模型（target）一次驗證**這串猜測。猜對的留下，猜錯的從分歧點重來。目標是**少跑幾輪大模型 decode**，在輸出分佈不變（或幾乎不變）的前提下把延遲壓下去。後端類比：像「樂觀鎖／預測執行」——先大膽往前跑，再用權威路徑校驗。

## 面試短答

- **問題**：自回歸 decode 串行；大模型每步都很貴，但單步算力利用率常偏低。
- **做法**：draft 提出 \(k\) 個候選 token → target **一次 forward** 對這 \(k\) 個位置做驗證（可並行比對 logits）→ 接受最長共同前綴，從第一個拒絕處改用 target 的真實採樣接上。
- **正確性**：標準 speculative decoding 在設計好的接受規則下，**輸出分佈等價於只跑 target**（不是「近似加速」那種亂猜）。面試要講「等價／近似」分清楚。
- **加速何時有用**：draft 夠準（接受率高）、\(k\) 選得好、target 顯存／帶寬瓶頸明顯。接受率低時反而多做無效 draft。
- **和 continuous batching／KV**：每個請求仍有自己的 KV；投機只是改變「每輪提出／驗證幾個 token」。要跟 batch 調度一起看，不是單獨銀彈。
- **和 Medusa／多頭草稿、n-gram／prompt 查找表**：同一家族——用便宜方式提案、貴模型驗證；實作細節不同，面試講清「提案＋驗證」框架即可。
- 後端類比：draft ≈ 快取／預測路徑；target verify ≈ 權威服務校驗；接受率 ≈ 預測命中率。

## 常見追問（含答案）

**Q：為什麼「小模型草稿」不會改變大模型的回答風格？**  
A：驗證步驟用的是 **target 自己的 logits／採樣規則**。草稿只決定「試哪些位置」；被拒絕後從 target 分佈重採。標準演算法保證與純 target 採樣同分布（在假設成立時）。若你們做了「直接採用草稿、不嚴格驗證」那就是近似，要另說品質風險。

**Q：接受率低怎麼辦？還要不要開 speculative？**  
A：先量 **平均接受長度／token 加速比／TTFT／TPOT**。接受率低常見原因：draft 太弱、任務太難猜（程式碼、罕見領域）、\(k\) 太大。可換更強 draft、縮小 \(k\)、只對長生成開、或關掉。瞎開會多耗 CPU／小模型 GPU 卻沒加速。

**Q：和「更大的 batch／量化／更短 prompt」比，何時優先 speculative？**  
A：量化／縮 prompt／RAG 減 context 是降成本與 prefill；batch 偏吞吐。Speculative 主要打 **單請求 decode 延遲**（聊天、低併發、長回答）。高併發時 GPU 已被 batch 吃滿，投機收益變小，甚至搶資源。面試答「看瓶頸在 TTFT/TPOT 還是 GPU 利用率」。

**Q：自建 vLLM／TGI 和調 API 時怎麼談這個？**  
A：自建可選引擎是否支援 speculative／草稿權重與調度。調 API 時供應商可能已內建，你只能看 SLA／延遲曲線，無法自己掛 draft。設計閘道時不要假設「換模型一定同延遲形態」。

## 小練習

**題：** 線上客服 P99 TPOT 偏高，GPU 利用率只有 ~40%。有人提議掛 1B draft 做 speculative。你會要哪三個數據才決定開不開？開了之後用什麼指標判斷成功？  

**參考答案：**  
1. **現況瓶頸**：單請求 decode 是否真的受制於串行步數（vs 排隊、prefill、KV 換出）。  
2. **草稿契合度**：同領域小樣上 draft 對 target 的 **token 接受率／平均接受長度**；太低直接否決。  
3. **資源賬**：draft 要佔哪張卡、是否擠掉主模型 batch、額外成本。  
成功指標：P95/P99 **TPOT 下降**、單位請求 wall time 下降、**輸出品質／自動評分無回歸**、GPU 有效吞吐不降（或可接受的小降）；若接受率 < 某閾值或延遲無改善就回滾。
