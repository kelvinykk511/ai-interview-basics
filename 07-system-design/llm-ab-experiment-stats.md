# LLM A/B 實驗統計（單位、功效、Peeking、護欄）

> 2026-11-10 · AI warm-up · 工程面試向  
> 上線節奏（shadow → canary → 護欄）見 [`online-llm-eval-canary.md`](./online-llm-eval-canary.md)、[`rag-shadow-eval.md`](./rag-shadow-eval.md)；**本篇只講：點設計實驗、點先唔會被「睇落好啲」騙。**

## 人話

換 prompt、換模型、改 top-k，唔係「dashboard 分數高咗就全量切」。輸出係文字、同一用戶會連住問幾輪、方差又大——好似 CEX 改出金文案或者風控提示：你要先定「邊啲人睇到新版、睇幾耐、邊個指標話贏、邊個指標只可以否決」。面試官想聽嘅唔係 p-value 公式，而係：**隨機單位、主指標 vs 護欄、樣本夠唔夠、仲有你有冇中途偷睇就宣布勝利。**

## 面試短答

- **隨機單位用 user（或 session），唔用 request。** 同一用戶今日 A 明日 B，學習效應同跨請求相關會污染；方差亦會被低估，假陽性更高。用 sticky feature flag（`hash(user_id, exp_id)`）鎖死組別。
- **主指標同護欄分開。** 主指標決定「贏唔贏」（任務完成率、一次性解決、升級率、授權後嘅 CSAT）；護欄只能否決、唔可以當勝利理由（TTFT/P99、成本 per req、拒答率異常、安全命中、JSON／工具失敗、投訴）。安全／合規破線 → 即回滾，唔好等實驗結束。
- **先算功效（power），再開實驗。** 預先釘：最小效應（例如完成率 +2pp）、顯著水準、功效（通常 80%）、實驗期。LLM 輸出同用戶路徑方差大，兩日幾百條就宣稱贏，樣本通常不夠。
- **禁止無計劃 peeking。** 日日睇 p 值、見到 <0.05 就切＝反覆檢定，假陽性會飆。做法：固定視窗先睇；或者一開始就用 sequential／always-valid CI，預先寫明可睇嘅時間點。
- **先查 SRM（Sample Ratio Mismatch）。** 預期 50/50（或 10/90 canary），實際差出統計範圍就要停：旗標 sticky 壞咗、cache key 未隔離、bot／健康檢查、客戶端本機賦值、某臂延遲高被取消。SRM 未修，後面分數唔可信。
- **相關同聚合。** 同一用戶多輪相關，要先按 user 聚合再比，或用 cluster-robust；唔好把 1 萬條訊息當 1 萬個獨立樣本。
- **降方差可以用實驗前協變量**（CUPED 思路）：用實驗前完成率／活躍度做調整，功效更高。唔好用實驗期間先被處理影響嘅變量當協變量。
- **新奇／學習效應。** 語氣或版面一變，頭兩日 CSAT 升或跌都可能係新鮮感。主結論要用完整預定期，必要時丟掉 burn-in 再估長期。
- **多重比較。** 同時盯 8 個 judge 分數，總有一個「顯著」。預先釘一條主指標；其餘當探索，要校正或多檢定策略。
- **Judge 只係代理指標。** 線上 LLM-as-judge 有位置／冗長／自我偏好偏差，只能輔助；**被測模型唔可以同時當 judge**。最終仍要對齊業務指標。
- **非劣效（non-inferiority）好常見。** 換平／換快模型，目標往往係「品質唔差過 δ」，唔係「一定要贏」。假設同樣本量要按非劣效嚟設，唔好套用「要贏先切」嘅優效框架。
- **後端類比：** sticky 賦值 ≈ 網關一致哈希；SRM ≈ 分流比例同觀察流量對唔上；peeking ≈ 盤中睇 PnL 就改策略；護欄 ≈ SLO 熔斷，唔係 KPI 達標。

## 常見追問（連答案）

**Q1：點解唔可以按 request 隨機？同一用戶兩邊都試唔係更公平嗎？**  
A：單次體驗對比好似公平，但其實（1）用戶會帶住上一輪語氣同記憶問下一輪，臂之間互相污染；（2）同一人多次請求高度相關，當獨立樣本會令標準誤偏細、更容易「顯著」；（3）產品承諾同快取（prompt cache、對話狀態）會亂。要同一人只喺一臂，先按 user 聚合。搜尋／RAG 召回先比可以用 interleaving；整段生成式回覆通常仍要用戶級 A/B。

**Q2：Canary 開咗兩日，dashboard p=0.04，可唔可以提早全量？**  
A：唔可以——除非你預先用咗允許中途決策嘅序貫方法，而且樣本同護欄都達門檻。普通 t-test／「睇到 0.05 就停」會膨脹 Type I error。正確係：預先寫實驗期同最小樣本；期滿先做一次主分析；護欄破線先至提前停（呢個係安全停止，唔係因為「好咗」而停）。

**Q3：Judge 分升咗，CSAT／解決率冇變，甚至升級率升咗，點判斷？**  
A：代理指標同業務指標唔對齊時，**跟業務同護欄**。可能係 judge 偏愛更長、更客套嘅回覆，用戶其實覺得囉嗦、解決唔到。抽差異樣本做人工，檢查長度／拒答／工具成功率；必要時重新校準 judge，唔好單靠分數切全量。

**Q4：點減少 bot、內部員工、重試請求對實驗嘅污染？**  
A：賦值前過濾健康檢查同已知 bot；內部帳號單獨層或不入主分析；按 `user_id` 而非 IP／request_id 賦值；取消／超時要兩邊定義一致（某臂慢會有更多「取消」被當成失敗）。分析集同「計費／SLO 集」分開寫清楚。

**Q5：同時改模型同 prompt，點拆？**  
A：一開始就交織因素會分唔清功勞。理想係一次一因素，或者 2×2 但每格都有足夠樣本。上線旗標都要可獨立回滾（模型 id、prompt 版本分開）。RAG 還要對齊檢索快照，否則你比緊嘅係檢索差，唔係生成差。

## 小練習

**題：** 客服 bot 想把主模型從 A 換到平 30% 嘅 B。Canary 1%、按 request 隨機，開咗 36 小時。線上 LLM-as-judge（就係模型 B 自己打分）平均 +0.08（p=0.04）；成本確實 −30%；拒答率 3% → 6%；CSAT 樣本只有 80 份、差唔多持平。同事建議「品質升咗又平，今日全量」。你會唔會切？正確實驗點設計？

**參考答案：**  
1. **唔切。** 隨機單位錯（request 級）、peeking、judge 同被測模型唔獨立、拒答率翻倍係護欄紅燈、CSAT 樣本遠遠不夠。p=0.04 喺呢個設計下唔可信。  
2. **重做：** `hash(user_id, exp_id)` sticky；預先釘主指標（例如 7 日任務完成率／一次解決）同非劣效邊界 δ（換平模型係「唔差過 δ」，唔係一定要贏）；護欄包括拒答、安全、JSON／工具失敗、TTFT、成本。  
3. **樣本／視窗：** 按歷史方差算功效，夠先停；禁止日日 p 值停實驗。先查 SRM。Judge 用獨立模型＋已校準 rubric，只當輔助。  
4. **拒答 6%：** 先做誤差分析（係更安全定係誤殺），分意圖睇；護欄破線應暫停擴量，唔係當「品質贏」。  
5. **通過先 1%→5%→20%**，留 holdout 睇新奇效應消退後嘅長期表現；旗標可秒切回 A。
