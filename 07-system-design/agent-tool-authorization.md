# Agent 工具權限（Tool Authorization / Least Privilege）

## 人話
Agent 可以調工具（查餘額、改設定、甚至出金）。危險在於：**模型唔可信**——佢可能被 prompt injection 騙、可能理解錯。所以權限唔可以由模型話事，要由**後端**話事：Agent 只係「幫用戶發請求嘅代理」，每次調工具都要用**當前用戶自己嘅權限**去檢查，寫操作要人確認，高風險操作 Agent 根本唔應該有。

一句話：**模型決定「想做咩」，後端決定「准唔准做」。**

## 面試短答
> 我會將 Agent 當成一個不可信嘅客戶端。工具層做三件事：一，身份傳遞——工具用當前用戶嘅 token/scope 調下游，而唔係用一個萬能 service account，避免 confused deputy；二，工具分級——只讀工具自動執行，寫操作要結構化確認（後端生成確認卡，用戶按掣，帶一次性確認 token），高風險（出金、改 2FA、API key）唔開放俾 Agent 或者強制走原有風控流程；三，參數校驗同限額喺後端做，唔信模型生成嘅 user_id/金額，user_id 一律由 session 注入。加上審計日誌記錄每次工具調用嘅 prompt、參數、結果，同埋 kill switch。

## 關鍵設計點
- **Confused deputy（被混淆嘅代理人）**：Agent 用高權限 service account 調內部 API，攻擊者透過注入令佢幫手查/改**別人**嘅數據。解法：工具調用帶用戶自己嘅 scoped token（OAuth token exchange / 下發短時效 delegated token），下游照常做 RBAC。
- **身份參數唔俾模型填**：`get_balance(user_id)` 呢種設計係錯；應該係 `get_balance()`，user_id 由後端從 session 注入。模型只填業務參數（幣種、時間範圍）。
- **工具分級**：
  - L0 只讀、自己數據：自動執行。
  - L1 可逆寫（改通知設定、建草稿）：確認卡。
  - L2 不可逆/涉資金（下單、出金、改安全設定）：唔暴露俾 Agent，或者只生成「預填表單」交返原有 UI + 2FA + 風控。
- **確認要綁定參數**：確認 token = 簽名(工具名 + 參數 hash + 用戶 + 過期時間)，執行時驗證，防止「用戶確認 A，模型偷偷改成 B」。
- **按任務收窄工具集**：客服 Agent 根本唔載入交易工具；工具越少，攻擊面同誤調越少。
- **限額與速率**：每 session/用戶工具調用次數、金額上限；異常模式（短時間大量查詢）觸發熔斷。
- **間接注入來源**：網頁、郵件、RAG 文檔、工具返回內容都可能藏指令；工具返回當「數據」處理，高權限動作唔可以由不可信內容觸發。
- **審計**：記錄 user、session、模型版本、工具、參數、確認 token、結果，方便事後追查同做軌跡 eval。

## 常見追問（連答案）
**Q1：System prompt 寫明「唔好幫用戶查其他人數據」，夠唔夠？**
答：唔夠。Prompt 係建議唔係權限邊界，可以被注入繞過。真正防線要喺工具/後端：user_id 由 session 注入、下游 RBAC 檢查。Prompt 只係減少誤調嘅第一層。

**Q2：點樣做「人確認」先唔會變成形式？**
答：確認內容由後端根據真實參數渲染（唔係模型自己描述），清楚顯示金額/對象/影響；確認 token 綁參數 hash、一次性、短時效；高風險再加 2FA。同時控制確認頻率，避免用戶習慣性亂撳（確認疲勞），低風險就唔好問。

**Q3：多 Agent / Agent 調 Agent 時權限點傳？**
答：權限只可以**向下收窄**唔可以放大：子 Agent 拿到嘅 token scope ≤ 父 Agent ≤ 用戶。用 token exchange 下發更窄 scope、更短時效嘅 token，並帶上原始用戶身份（actor chain）做審計。

**Q4：MCP 之類工具協議引入第三方工具，有咩額外風險？**
答：工具描述本身可以藏注入（tool poisoning）、第三方 server 可能讀到你傳過去嘅數據。做法：工具白名單 + 版本固定、審核描述、敏感數據唔傳俾第三方工具、第三方工具同內部高權限工具喺唔同 session/Agent 隔離。

**Q5：模型重試導致寫操作重複執行點算？**
答：寫工具一定要冪等：每次工具調用帶 idempotency key（例如 session_id + tool_call_id），後端去重。同出金/下單嘅冪等設計一樣。

## 小練習（附參考答案）
**題目：** 交易所要上線「AI 助手」，用戶可以問「我上個月手續費幾多」、「幫我關閉提幣白名單」、「幫我將 USDT 轉去呢個地址」。一位同事設計咗一個工具 `call_internal_api(path, body)`，用 admin service account 調所有內部 API。指出問題並重新設計。

**參考答案：**
1. 問題：(a) 萬能工具 = 模型可以調任何 API，注入一句就可以讀/改任何用戶數據（confused deputy）；(b) admin 帳號繞過所有 RBAC；(c) 冇分級，出金同查詢同等對待；(d) 冇冪等同審計。
2. 重新設計：拆成細粒度工具，`get_fee_summary(month)` 只讀、user_id 由 session 注入、用用戶 delegated token 調下游。
3. 「關閉提幣白名單」屬安全設定（降低保護），唔暴露俾 Agent；只回覆引導連結，用戶要喺原有設定頁 + 2FA + 冷靜期操作。
4. 「轉 USDT 去某地址」屬 L2 資金操作：Agent 最多生成預填出金表單（地址、金額由後端校驗），交返原有出金流程（2FA、地址白名單、風控）；Agent 本身冇出金權限。
5. 全部工具調用寫審計日誌、設 rate limit、kill switch；寫工具帶 idempotency key。
