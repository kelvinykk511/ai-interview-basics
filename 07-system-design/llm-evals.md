# LLM / RAG 評估（Evals）

## 人話

模型輸出不像 API 回 JSON 那樣「對／錯」一眼能判。沒有評估，你只是「感覺變好了」。工程上要把評估拆成：**離線（改完先跑一套固定題）**和**線上（真實流量抽樣）**，再分開量「檢索有沒有找對」和「生成有沒有據實回答」。

## 面試短答

- **Golden set**：一小組（可從幾十到幾百）「問題 → 期望要點／引用／不該說什麼」。改 prompt、embedding、chunk、model 都先跑這套，避免憑感覺上線。
- **RAG 常拆兩層：**  
  - 檢索：召回率＠k、MRR、命中是否含正確文檔／段落。  
  - 生成：忠實度（有沒有脫離檢索胡謅）、相關性、完整性、格式／拒答是否正確。  
- **自動打分：** 規則（必含關鍵詞、JSON schema）、LLM-as-judge（另一模型依 rubric 打分）、embedding 相似度。都有偏差，要抽樣人工對齊。  
- **線上指標：** 用戶點踩、重問率、人工抽檢、工具呼叫成功率、延遲／成本。離線過關 ≠ 線上一定好。  
- 和後端類比：golden set ≈ 回歸測試；線上抽樣 ≈ canary + 人工審；LLM-as-judge ≈ 用另一服務做近似斷言，不能當唯一真相。

## 常見追問（含答案）

**Q：只有「回答好不好」一個分數夠嗎？**  
A：不夠。檢索錯但文筆好、或檢索對但胡謅，分數會混在一起。至少拆「找得到嗎」和「據實寫了嗎」，才知道該調向量庫還是 prompt／模型。

**Q：LLM-as-judge 可靠嗎？**  
A：便宜、可擴，但會偏偏好長文、跟裁判模型口味。要固定 rubric、打亂順序、抽樣人工標註算一致性；關鍵安全／合規題仍要人審或硬規則。

**Q：怎麼防回歸？**  
A：CI 跑 golden set（檢索＋生成）；改 embedding／chunk 策略要重建索引並對比舊集；設門檻（例如忠实度低於 X 不准發）。搭配線上 canary 與點踩監控。

## 小練習

**題：** 你們把 chunk 從 500 token 改成 200 token，線上「感覺」變好，但客訴「答非所問」沒降。怎麼用 eval 證明有沒有變好？  

**參考答案：**  
1. 建／擴 golden set：含「答案在單一段落」與「要跨多段」的題。  
2. 離線對比舊新索引：檢索 hit＠k、MRR；生成忠实度／相關性（規則 + judge + 人工抽樣）。  
3. 若檢索變好但客訴仍在：看是不是 top-k 變了卻沒重排、或 prompt 沒要求「檢索不到就說不知道」——用分層指標定位，而不是只看一個「整體分」。
