# 長對話上下文管理：截斷、摘要與記憶

## 人話

LLM 本身冇記憶，每次請求都係「無狀態」：多輪對話之所以記得上文，係因為後端每次把**歷史訊息重新塞入 prompt**。對話越長，token 越多 → 成本、延遲（prefill）線性上升，最後撞 context window 上限。而且就算塞得落，模型對**中間段**內容嘅注意力會變差（lost in the middle）。

所以後端要決定：每次請求帶邊啲歷史、點樣壓縮、邊啲要長期記住。類比：HTTP 無狀態，session 狀態放 Redis，每次請求按需載入——唔係把成個 session log 都傳俾 handler。

## 面試短答

- **Token 預算先行**：`context window = system + 工具定義 + 長期記憶 + 檢索內容 + 歷史 + 本輪輸入 + 預留輸出(max_tokens)`。先為每段定上限，超咗按優先級裁剪，**輸出預留一定要扣起**，否則答案被截斷。
- **策略由簡到繁**：
  1. **滑動窗口**：保留最近 N 輪（按 token 計，唔係按條數）。簡單，但會忘記早期關鍵信息（例如用戶開頭講咗自己用 Java 17）。
  2. **滾動摘要**：舊對話用便宜模型壓成摘要，新對話原文保留——「摘要 + 最近 K 輪原文」。
  3. **結構化記憶**：抽取事實（偏好、約束、已確認決定）存成 key-value／條目，按需檢索注入（memory 即係對自己歷史做 RAG）。
- **永遠唔好裁走的**：system prompt、本輪問題、仍在進行中的 tool call 及其結果的配對（assistant tool_call 同 tool result 要成對保留，否則 API 報錯或模型混亂）。
- **工具結果係大頭**：一次 tool call 返回幾千 token JSON，之後每輪都重複付費。只保留摘要／關鍵欄位，原文存外部，需要時再查。
- **對 prompt cache 友好**：歷史係「穩定前綴」——只在尾部追加就可命中 prefix cache；但每輪重寫摘要會令前綴變動 → miss。所以摘要要**分段、低頻**更新（例如每累積 20 輪先壓一次），唔好每輪重算。

## 常見追問（含答案）

**Q：摘要有咩風險？**  
A：①**失真**：摘要模型漏咗否定、數字、約束（「唔好用 Redis」變成「討論咗 Redis」）；②**遞歸漂移**：摘要的摘要再摘要，細節逐層流失；③**成本延遲**：摘要本身係一次 LLM 調用。對策：摘要 prompt 明確要求保留決定、約束、數字、未解決問題；用結構化格式（已確認事實／用戶偏好／待辦）而唔係散文；異步後台做，唔阻塞用戶請求；原文保留喺 DB，摘要只係「視圖」，可以重算。

**Q：滑動窗口按「條數」定有咩問題？**  
A：每條長度差異巨大（一句「好」vs 一段貼上的 3000 行 log）。按條數會間歇爆 context 或浪費空間。應該用與模型一致的 tokenizer 計 token，按預算從最新往回裝。

**Q：用戶話「返去我哋第一個方案」，但第一個方案已經被裁走點算？**  
A：這正是結構化記憶／歷史檢索的用途：把完整歷史存 DB 並建 embedding 索引，當本輪問題指涉舊內容時，檢索相關舊訊息片段注入。或者摘要中明確記錄「方案列表及編號」。只有滑動窗口的話就會答錯或亂編。

**Q：長期記憶（跨會話）點設計？要注意咩？**  
A：寫入：從對話抽取穩定事實（偏好、身份、長期目標），帶來源、時間戳、置信度；讀取：按相關性＋新近度檢索 top-k 注入。要注意：①**衝突與更新**（舊事實被新事實覆蓋，唔好兩條矛盾並存）；②**隱私**：用戶可查看／刪除，敏感資料唔記或加密；③**注入攻擊**：記憶內容來自用戶輸入，可能被寫入惡意指令，注入時要當成數據而非指令；④多租戶隔離。

**Q：Context window 越嚟越大（百萬 token），仲需要管理咩？**  
A：需要。①成本同 prefill 延遲隨 token 線性（甚至更差）增長，百萬 token 一次請求好貴；②lost in the middle：塞越多，關鍵信息越易被忽略，品質未必升；③KV cache 佔顯存，自建時直接影響併發。大 window 係「上限放寬」，唔係「唔使設計」。

**Q：點樣評估上下文管理策略？**  
A：建長對話測試集：早期埋入關鍵事實／約束，後期提問依賴佢（needle-in-conversation）；度量事實保持率、約束違反率、每輪平均 input tokens、P95 延遲、摘要觸發頻率。比較「全量歷史 vs 窗口 vs 摘要+窗口 vs +記憶檢索」。

## 小練習

**題：** 你負責一個代碼助手，平均會話 60 輪，每輪用戶會貼 log 或代碼，模型 context 128k。上線一個月發現：長會話後期答案開始「忘記」用戶早期講過的技術棧約束，而且單會話成本後期每輪暴漲。你點改？

**參考答案：**
1. **定 token 預算**：system+工具 ~4k、長期記憶 ~1k、摘要 ~2k、最近原文 ~20k、本輪輸入上限、輸出預留 ~4k；按 tokenizer 計。
2. **最近 K 輪原文 + 分段滾動摘要**：超出窗口的舊輪次每累積一段才異步壓縮一次（保持前綴穩定，命中 prompt cache）；摘要用結構化格式：技術棧／約束／已做決定／未解決問題。
3. **約束提升為「置頂事實」**：用戶聲明的技術棧、版本、禁止事項抽取成會話級記憶，固定放喺 system 之後，唔受窗口裁剪影響。
4. **大塊貼上內容外置**：log／代碼原文存儲，歷史中只留摘要＋引用 ID；需要時用檢索或工具重新讀取，避免每輪重複付費。
5. **評估**：長會話回歸集測約束違反率同事實保持率；監控每輪 input tokens 曲線應趨平，而唔係隨輪數線性上升。
