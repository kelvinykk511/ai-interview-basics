# Multi-Agent 編排：Supervisor、Handoff、幾時唔好用多 Agent

> 2026-11-05 · AI warm-up · 工程面試向

## 人話

「Multi-agent」即係將一個大任務拆俾幾個各有 prompt + 工具嘅 LLM 角色去做。常見三種形狀：

- **Supervisor / Orchestrator–Worker**：一個主控 agent 拆任務、派俾 worker（研究、寫 SQL、審核），收結果再合併。好似後端嘅 **scatter-gather**。
- **Handoff（交接）**：一個 agent 做到一半將對話「轉駁」俾另一個（客服分流 → 退款專員）。好似 **狀態機轉移**，同一時間只有一個 agent 揸住對話。
- **Pipeline / 固定 workflow**：步驟寫死喺代碼（檢索 → 抽取 → 校驗 → 生成），每步可以用 LLM，但流程唔由 LLM 決定。

重點：**多 agent 唔係越多越聰明**。每加一個 agent 就多一層 LLM 調用（延遲、token 成本）、多一個會出錯嘅交接位、debug 難度指數上升。業界共識係：**能用固定 workflow 就唔好用 agent；單 agent + 好工具搞得掂就唔好用 multi-agent**。

## 面試短答（30 秒版）

> 我會先問任務係咪真係需要多 agent。適合嘅場景係：子任務可以**並行**且彼此獨立（例如同時查幾個數據源）、或者需要**唔同權限/工具集隔離**（讀 agent 同寫 agent 分開）、或者單個 context 塞唔落。設計上我用 supervisor 模式：主控只負責拆解同合併，worker 拎**明確嘅任務描述 + 最小 context**，回傳**結構化結果**而唔係長篇對話；所有狀態放喺外部（durable workflow），每步有超時、重試上限、總 token/步數預算；最後用軌跡評估分開量度「拆得啱唔啱」同「每個 worker 做得啱唔啱」。

## 常見追問（連答案）

**Q1：Supervisor 同 Handoff 點揀？**
A：任務可以拆成獨立子任務、要合併結果 → supervisor（scatter-gather）。對話式、按階段由唔同專家接手、同一時間只需一個角色 → handoff。Handoff 要注意交接時**帶乜 context 過去**：成段歷史太貴又帶入無關指令，只帶摘要又可能漏關鍵資訊；實務係傳「結構化交接單」（用戶意圖、已驗證身份、已收集欄位）+ 必要時可查原始記錄。

**Q2：Multi-agent 最常見嘅失敗模式？**
A：
1. **無限循環 / 互相踢波**：A 叫 B 做，B 話要 A 確認。→ 全局最大步數、最大 token、檢測重複調用。
2. **錯誤放大**：worker 幻覺出嚟嘅結果，supervisor 當真再派下一步。→ worker 輸出用 schema 校驗，關鍵事實要帶出處，supervisor 可以要求證據。
3. **Context 污染**：worker 讀咗不可信內容（網頁、工單），返回時夾帶 prompt injection 俾 supervisor。→ worker 輸出當數據唔當指令，寫操作權限唔放喺讀外部內容嘅 agent 度。
4. **重複工作 / 衝突寫入**：兩個 worker 同時改同一份資源。→ 分配時劃清邊界（按資源分區），寫操作經單一 executor + 冪等鍵。
5. **成本爆炸**：一個問題觸發十幾次大模型調用。→ worker 用細模型，只喺拆解同最終合併用大模型。

**Q3：狀態放邊？**
A：唔好只放喺 LLM 對話記錄入面。用外部持久化狀態（task 表或 durable workflow 引擎如 Temporal）：每個子任務有 id、狀態、輸入、輸出、重試次數。好處係進程死咗可以續跑、可以審計、可以只重跑失敗嘅 worker。同後端 saga 一樣，有副作用嘅步驟要冪等或者有補償。

**Q4：點樣評估 multi-agent 系統？**
A：分層評估：(1) 端到端任務成功率；(2) **規劃層**——拆解出嚟嘅子任務集合啱唔啱、有冇多餘步驟；(3) **執行層**——每個 worker 用獨立 golden set 單元測試；(4) 效率指標——平均步數、token、P95 延遲。用 trace（每個 agent 調用係一個 span，帶 parent id）先可以定位係邊一層出事。

**Q5：點解有時單 agent 反而好過 multi-agent？**
A：交接會丟資訊（每次轉手都係有損壓縮）、多一層延遲、而且模型之間決策唔一致。如果子任務高度相關（要共享大量細節），一個 agent 揸住完整 context 通常更準。Multi-agent 嘅收益主要嚟自**並行**同**隔離**，唔係嚟自「更多大腦」。

## CEX 例子

「用戶投訴提現未到帳」：
- 固定 workflow 已經夠：查提現單 → 查鏈上 tx → 查風控狀態 → 生成回覆。步驟明確，唔需要 agent 自己規劃。
- 如果係「幫合規團隊調查一個可疑帳戶」：supervisor 並行派三個**只讀** worker（交易記錄、鏈上地址關聯、KYC 資料），各自回結構化摘要 + 證據 id，supervisor 合併成報告。**凍結帳戶**呢類寫操作唔交俾任何 agent 自動做，出確認卡由人批。

## 小練習（題目 + 參考答案）

**題目：** 你哋個 multi-agent 研究助手上線後，平均每個請求調用 LLM 23 次、P95 延遲 90 秒，偶爾仲會跑到 200 次先停。你會點診斷同改？

**參考答案：**
1. **先睇 trace**：按 agent 分組統計調用次數同 token，搵出邊個 agent / 邊對 agent 之間有循環（例如 reviewer 不停打回 writer）。
2. **加硬性預算**：全局最大步數（例如 15）、每個 worker 最大重試（2）、總 token 上限；超咗就返回部分結果 + 說明，而唔係無限跑。
3. **改拆解策略**：獨立子任務並行執行（降延遲）；高度相關嘅子任務合併返俾同一個 agent（減交接）。
4. **收窄 worker 輸出**：要求 schema 化結果，reviewer 打回時必須講具體缺陷，冇具體缺陷就視為通過，避免「感覺唔夠好」式循環。
5. **模型分級**：worker 用細模型，supervisor/最終合併用大模型。
6. **回歸驗證**：改完用同一批 golden 任務比較成功率、平均步數、P95，確保唔係靠「早啲停」換嚟差啲嘅質量。
