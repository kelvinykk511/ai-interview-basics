# 線上 LLM 評估：Shadow、Canary 與護欄指標

## 人話

離線 golden set 只能證明「這批題還行」。真正上線要回答：**新 prompt／新模型／新檢索參數，會不會搞砸真實用戶？** 做法借後端釋出：先 **shadow（影子流量，只觀察不影響用戶）**，再 **canary（小比例真實流量）**，用一組 **護欄指標（guardrail metrics）** 決定推進或回滾。和推 Java 服務一樣——差別是輸出是文字，對錯更難自動量，所以要混用自動分數、業務指標與抽樣人工。

## 面試短答

- **離線 vs 線上**：離線 = 固定集可回歸、可 CI；線上 = 分佈漂移、真實 prompt、延遲與成本。兩者都要，缺一不可。
- **Shadow**：同一請求打新舊兩條路徑，**只把舊的回給用戶**；比較輸出／分數／延遲／成本。注意隱私、雙倍費用、以及「影子路徑失敗不能拖垮主路徑」。
- **Canary**：1%→5%→… 真實用戶看到新版本；要有 **快速回滾** 與 **按租戶／功能開關**（feature flag）。
- **護欄指標（建議分層）**：  
  - 系統：TTFT/TPOT/錯誤率/超時/取消率/成本 per req  
  - 品質代理：拒答率、引用校驗失敗率、結構化 JSON 解析失敗、工具呼叫失敗率、安全過濾命中  
  - 業務：CSAT、工單升級率、任務完成率、退款／投訴  
  - 抽樣：每日 N 條人工或 LLM-as-judge（有偏差，只能當輔助）
- **統計**：要講清樣本量與「看起來好一點」vs「顯著」；LLM 方差大，別用一天 20 條就全量切。
- 後端類比：shadow ≈ 雙寫／鏡像讀；canary ≈ 金絲雀發布；護欄 ≈ SLO + 業務 KPI；feature flag ≈ 配置中心開關。

## 常見追問（含答案）

**Q：文字輸出怎麼自動比「好不好」？沒有單一正確答案怎麼辦？**  
A：任務分型。有標準答的（抽欄位、分類、SQL）用 exact／結構校驗；開放生成用 **成對偏好（A/B 人工或 judge）**、引用是否可後端核實、安全規則、長度／格式約束。不要只靠「LLM 打 1–5 分」一條線決策。

**Q：Shadow 雙倍打模型，成本與一致性怎麼控？**  
A：抽樣 shadow（例如 5% 請求）、只 shadow 非敏感租戶、非尖峰時段；影子路徑獨立限流與超時，**失敗吞掉**。比對要對齊同一 `request_id`、同一檢索快照（RAG 要記 retrieval 結果），否則比的是「檢索差」不是「生成差」。

**Q：Canary 時舊版快取／prompt cache 會不會讓對比不公平？**  
A：會。新舊版本 **cache key 要隔離**（模型 id、prompt 版本、檢索參數納入 key）。否則 canary 冷啟動看起來更慢更貴，誤判回滾。

**Q：誰有權切全量？面試怎麼講治理？**  
A：預先訂 **進階門檻**（護欄全綠 + 最低樣本 + 無 P0 安全事件）與 **自動回滾條件**（錯誤率、拒答異常、成本暴衝）。人審只處理灰色地帶。強調「模型發布 = 配置發布」，走同一套審批與審計。

## 小練習

**題：** 你們要把客服 bot 的 system prompt 從 v3 換到 v4，同時 retrieval top-k 從 4 改 8。設計一個一週內的上線計劃（含回滾），並列出至少五個你會盯的指標。  

**參考答案：**  
1. **離線**：用 golden + 回歸集跑 v4；引用核實／JSON schema／安全集不能變差。  
2. **Shadow 2–3 天**：5–10% 流量雙跑；對齊 retrieval 快照；比對延遲、成本、解析失敗、引用失敗；主路徑超時與影子解耦。  
3. **Canary**：1% → 5% → 20%，每階看滿約定樣本；feature flag 按租戶可秒切回 v3。  
4. **指標**：TTFT/TPOT P99、5xx／超時、成本 per req、JSON／工具失敗率、引用校驗失敗、拒答率異常、CSAT／升級率；另設安全命中告警。  
5. **回滾**：任一護欄破線或安全 P0 → 自動回旗標；top-k 與 prompt **分開開旗**，出問題能定位是檢索還是提示詞。
