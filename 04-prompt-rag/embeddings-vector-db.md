# Embeddings 與向量庫取捨

## 人話

Embedding = 把一段文字變成一串數字（向量），「意思相近」的文字在空間裡距離也近。向量庫就是專門存這些向量、做「找最像」的資料庫。對後端來說：像「語義版倒排索引」——不是精確關鍵字 match，而是近似最近鄰搜尋。

## 面試短答

- **Embedding model**：同一套索引必須用同一模型（維度、空間一致）。換模型 ≈ 全量重嵌＋重建索引。
- **相似度**：常見 cosine／內積；正規化後兩者常等價。面試講「選一種並在評估裡固定」。
- **ANN（近似最近鄰）**：HNSW、IVF 等用圖／分桶換速度，召回不是 100%。調 `efSearch`／`nprobe` 是延遲 vs 召回的旋鈕。
- **混合檢索**：向量（語義）＋ BM25／關鍵詞（精確詞、代號、錯誤拼寫弱）。再加 **rerank**（交叉編碼器或小模型）重排 top-k。
- **Metadata filter**：租戶、權限、語種、時間——先過濾再搜或帶 filter 的索引，避免跨租戶泄露（CEX 後端直覺：多租戶隔離）。
- **何時不用純向量**：強精確匹配（訂單號、合約地址）、極短 query、需要可解釋關鍵詞命中時，混合或乾脆關鍵詞為主。

## 常見追問（含答案）

**Q：維度越高一定越好嗎？**  
A：不一定。更高維可能更細，但更吃存儲／距離計算；收益常遞減。以下游檢索／RAG golden set 為準，不是看 leaderboard 單一分數。

**Q：HNSW 和 IVF 怎麼選（面試層級）？**  
A：HNSW：建索引較吃記憶體，查詢延遲穩、召回好，中小到中大規模常用。IVF（＋PQ）：靠分桶＋壓縮省資源，適合超大規模，但參數調不好召回掉。實務：資料量、記憶體預算、P99 延遲、能否接受重建成本。

**Q：為什麼「只把問題 embed 去搜」還不夠？**  
A：用戶問法與文檔寫法分布不同（query-doc gap）；同義、代號、多語言會漏。解法：混合檢索、query 改寫／擴展、HyDE、rerank、以及權限與業務 metadata。

**Q：向量庫 vs Postgres `pgvector` vs 自建？**  
A：專用向量庫（Pinecone／Milvus／Qdrant 等）：ANN、過濾、規模化成熟。`pgvector`：和業務庫同事務／運維簡單，中小規模夠用。超大＋嚴格 P99 再專用。面試強調「先算 QPS、維度、過濾複雜度，再選」。

## 小練習

**題：** CEX 客服 RAG：文件含「充值不到帳」SOP，又有用戶 UID／訂單號。只用向量 top-5，線上常答錯流程或扯到別的產品線。你會改架構的哪三刀？  

**參考答案：**  
1. **混合檢索**：向量抓語義相近 SOP＋關鍵詞／過濾鎖產品線、語系、是否對該用戶可見。  
2. **Metadata／權限**：按租戶、產品（現貨／合約）、文檔狀態過濾，避免串線。  
3. **Rerank＋評估**：對候選重排；golden set 加「精確單號／產品名」題，分開看 hit＠k 與生成忠实度——別只調 embedding 模型。
