# GraphRAG／實體鏈接：community vs local、圖譜唔係唯一真源

> 2026-11-19 · AI warm-up · 工程面試向  
> 迭代檢索見 [agentic-iterative-retrieval.md](./agentic-iterative-retrieval.md)；去邊個庫見 [query-corpus-routing.md](./query-corpus-routing.md)；grounding 見 [grounding-citations.md](./grounding-citations.md)；多租戶 ACL 見 [multi-tenant-rag.md](./multi-tenant-rag.md)。**本篇講：幾時先值得建知識圖譜、實體點對到規範 ID、local／community（global）查詢點分工，以及摘要圖唔可以取代受控事實表。**

## 人話

普通 RAG 係「問句變成向量，撈最似嘅塊」。呢招對「ETH 喺 ERC-20 嘅 VIP 提現費幾多」通常夠——答案就喺某一行。但若問題係「呢季事故覆盤主要有邊幾類主題？」或者「提現政策喺各產品之間點互相引用」，相似塊未必覆蓋全貌，因為主題散落喺好多篇、而且要理解實體之間嘅關係。

**GraphRAG**（Microsoft 呢類做法係代表，唔係唯一實現）大致係：用 LLM 從文檔抽出實體同關係 → **實體鏈接**到規範節點 → 建成圖譜 → 用社區發現（常見 Leiden）分層群組 → 再為每個 community 生成摘要。查詢分兩路：**local** 從問句提到嘅實體出發，行鄰居同相關原文；**global／community** 則讀社區摘要（常係 map-reduce），用來答「整體有咩主題」。

後端類比：local 似按主鍵查一條產品同佢嘅關聯表；community 似先讀部門週報，再匯總，而唔係把全部工單 dump 俾模型。面試官想聽：同 hybrid／迭代檢索有咩分別、實體對錯會點 cascade、費用同增量更新、內部費率可唔可以信圖譜摘要。

## 面試短答

- **先問清問題類型，唔好一開始就建圖。** 單跳事實、錯誤碼、費率行，優先受控目錄／SQL／hybrid RAG。圖譜擅長「關係＋全域主題」；兩者可以並存，由路由決定（見 query-corpus-routing）。
- **實體鏈接係成敗關鍵，抽取只係第一步。** 抽出「ETH」「以太坊」「Ether」之後，要對到同一個產品 ID；同時要擋住「ETH」對成「ETHFI」。CEX 應用**產品目錄／詞表做權威**，LLM 抽取只係候選；對唔上就標未鏈接，唔好自動合併。
- **Local vs community 唔係兩個可互換嘅開關。** Local：問句有明確實體，沿鄰居取 entity 描述、關係、相關 community 報告同原文單元。Community／global：問句係主題／全庫概覽，對某一層社區摘要做 map-reduce。用錯會「說得很完整但引用唔到那一行」，或者「只盯住一個實體而看漏主題」。
- **社區摘要唔係 source of truth。** 摘要會過時、會寫滑、會把多篇口徑捏成一句。生成階段仍要能回落到原文／受控表做 citation；費率、限額、生效日只認受控表，唔認 community report。
- **建庫成本同增量都貴。** 抽取＋連結＋每層摘要，每次 ingest 都係多次 LLM，通常遠貴過一次 embedding。加一篇或改一行費率，可能影響節點、邊、甚至社區邊界。實務：規範實體用目錄增量 upsert；社區摘要定期重建；高變更源（費率）唔靠摘要做真值。版本釘 `graph_index_version`（抽取 prompt、連結詞表、社區層級、摘要 prompt）。
- **ACL 要喺建圖前硬過濾。** 社區摘要若跨過權限邊界，等於把受限 SOP 寫進共用週報。分租戶／分密級建圖，或只對已授權子圖查詢；唔可以先全球摘要再靠 prompt 話「唔好提機密」。
- **同迭代檢索可疊加，唔互相取代。** 第一跳可用圖譜做實體消歧或補關係；下一跳仍可定向去費率表。GraphRAG 唔自動解決「中間實體未出現」之外嘅全部多跳題，亦唔取代 BM25／rerank。
- **評估要分 slice。** 要有實體事實集（local＋連結正確性）、關係集、全域主題集（人手或受控大綱）。只報平均 Hit@k 會把「主題題全軍覆沒」或「摘要答對但引用咗錯費率」沖淡。監控未鏈接率、錯連率、摘要相對原文嘅 stale 率。

## 常見追問（連答案）

**Q1：已經有 hybrid + rerank + 迭代檢索，仲要唔要 GraphRAG？**  
A：唔係默認加。先用主題／關係類 slice 衡量現役缺口。若多數失敗其實係路由錯庫、詞表弱或單跳資訊不夠，先補呢啲。只有「要看關係或全庫結構」先值得付建圖成本。

**Q2：實體對錯會發生咩事？**  
A：錯連會令 local 行錯鄰居，後面每跳都圍繞錯產品——同迭代檢索嘅 error cascade 一樣。漏連會令同一實體裂成多個節點，community 同召回都碎。所以連結要以目錄為準，並單獨評估 linking 準確度，唔好只睇端到端分數。

**Q3：費率改咗，係咪改原文再 embedding 就夠？**  
A：對普通 RAG 可能夠；對 GraphRAG 唔夠。舊社區摘要同實體描述可能仲寫住舊費率。高變更事實應查受控表；圖譜只保留「邊個產品有提現費、指向邊張表」。改文後要讓受影響摘要失效或納入定期重建，禁止用過期 report 當答案。

**Q4：Global 查詢好慢、好貴，點控？**  
A：唔好每條請求對所有社區做全量 map-reduce。按問題類型路由：事實題走 local 或普通 RAG；主題題先選合適層級、可對社區摘要做檢索再只 map 頂層一批。預算寫死（社區數、LLM 次數、牆鐘）。結果仍要引用原文或受控表。

**Q5：可唔可以用用戶 prompt 叫模型「只查內部 SOP 圖譜」來當授權？**  
A：唔可以。ACL 喺檢索／建圖層執行，同多租戶篇同一原則。用戶或模型請求升權一律忽略。

## 小練習

**題：** 知識源包括：產品目錄（幣、鏈、費率，強一致）、活動公告（會過期）、幫助中心、有 ACL 嘅合規 SOP。同事建議全庫做一個 GraphRAG，「VIP ETH 提現費」走 local，「呢季客訴主題」走 community；費率變更只重嵌原文；SOP 同公開幫助中心共用同一層社區摘要，靠 prompt 叫模型唔好洩漏。你會點評，同埋會點落地？

**參考答案：**  
1. **全庫一張圖唔得。** SOP 同公開材料要分圖或分密級；社區摘要一旦跨權限就洩漏，prompt 擋唔住。  
2. **費率題唔應把 community／實體摘要當真值。** Local 最多用來消歧「ETH≠ETHFI」、確認鏈，最終數字查產品目錄／費率表。  
3. **只重嵌原文唔夠。** 舊摘要可能保留舊費率；目錄要即時更新，受影響 report 失效或定期重建。  
4. **主題題先做路由。** 「呢季客訴主題」可以走 community（只限有權數據），並設 map 預算；唔好每條事實查詢都全球 reduce。  
5. **落地：** 目錄做連結權威；`graph_index_version` 釘死；slice 分開實體事實／錯連／主題／ACL；生成引用受控表或原文，引用唔到就 abstain。
