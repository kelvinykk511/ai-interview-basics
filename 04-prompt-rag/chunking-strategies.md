# RAG Chunking 策略

## 人話

Chunking = 把長文件切成「檢索單位」。切太碎：一段話缺上下文，檢索到也組不出完整答案。切太粗：一段塞滿雜訊，embedding 變模糊，也容易撐爆 context window。後端類比：像設計 API 的「一頁回傳多大」——太大浪費帶寬，太小要打很多次才能拼齊。

## 面試短答

- **目標**：每個 chunk 盡量是「一個可獨立回答的語義單位」，同時保留足夠上下文（標題、章節路徑、前後句）。
- **常見切法**：固定 token／字元窗 + overlap；按段落／標題（Markdown heading）；按語義邊界（換話題再切）；結構化文件按表格列／FAQ 一問一答一切。
- **Overlap**：窗與窗重疊一段，避免答案剛好落在切開處；代價是索引膨脹、重複檢索。
- **Metadata 必帶**：`doc_id`、標題路徑、頁碼／章節、權限／租戶、版本／生效時間——檢索後過濾比「全靠向量」可靠。
- **與 embedding／rerank 的關係**：chunk 品質決定向量品質；壞切法再用貴模型也救不回來。Hybrid（BM25 + 向量）＋ rerank 可部分彌補，但根因仍在切塊。
- **CEX 直覺**：SOP／風控規則按「一條規則／一個狀態轉移」切；合約地址、幣種、網絡名不要被切斷到兩個 chunk。

## 常見追問（含答案）

**Q：固定 512 token + 10% overlap 夠不夠當預設？**  
A：當 MVP 可以，面試要補「依文件類型調」。FAQ／API error code 宜小塊；長篇政策／架構說明宜按 heading。量測用 retrieval recall@k，不要只憑感覺。

**Q：為什麼有 overlap 還會漏答案？**  
A：答案跨很多段、或關鍵詞在標題／表頭而正文在另一塊；或切在列表中間導致指代不清（「上述三項」）。解法：把標題路徑 prepend 進每個 chunk、表格整列保留、必要時 parent-child（小塊檢索、大塊送進 LLM）。

**Q：Parent-child / small-to-big 是什麼？**  
A：索引用小 chunk（檢索準），命中後把父段落／整節送進生成 context（上下文夠）。代價：實作複雜、要維護父子 id 映射。

**Q：多語言／程式碼怎麼切？**  
A：程式碼按函數／類別／符號邊界切，並保留檔名＋符號名在 metadata；中英混排避免在詞中間硬切（用 tokenizer 對齊模型）。法律／合規文件優先保留條款編號完整。

**Q：Chunk 大小和 context window、成本怎麼權衡？**  
A：檢索 top-k × 平均 chunk tokens 必須留空間給 system＋對話歷史＋輸出。k 大或塊大 → 更貴、更慢、更多雜訊。面試講：先定延遲／成本預算，再反推 k 與塊大小，用 eval 找甜蜜點。

## 小練習

**題：** 知識庫有三種文件：（1）客服 FAQ 一問一答；（2）長篇「提現風控 SOP」含多層標題；（3）錯誤碼表（code → 含義 → 處理步驟）。你會分別用什麼切法？各給一個理由。  

**參考答案：**  
1. **FAQ**：一問一答一切（或 Q+A 同塊）。理由：語義自洽，檢索命中即可答，避免把無關 FAQ 黏在一起。  
2. **長篇 SOP**：按 Markdown／標題層級切，chunk 前 prepend 標題路徑，適度 overlap；高風險步驟可 parent-child。理由：保留「在哪個章節」的上下文，又避免整章塞進一個向量。  
3. **錯誤碼表**：一行／一碼一切，metadata 帶 `error_code`。理由：查詢常是精確 code；整表一大塊會稀釋向量，也難做權限／版本過濾。
