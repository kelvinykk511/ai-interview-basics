# 文檔解析 Ingestion：PDF、表格、OCR

## 人話
RAG 效果好唔好，好多時唔係輸喺 embedding 或者模型，而係**第一步讀文件就讀錯**：PDF 兩欄排版讀到左右亂串、表格變成一堆冇欄名嘅數字、掃描件根本冇文字層、頁眉頁腳每頁重複污染檢索。

Ingestion 就係「將各種文件變成乾淨、有結構、帶 metadata 嘅文本塊」嘅 ETL 管道。後端思路完全適用：分階段、可重跑、冪等、有質檢、有死信。

## 面試短答
> 我會將 ingestion 做成分階段嘅異步管道：接收 → 類型識別 → 解析 → 清洗 → 結構化切塊 → embedding → 寫索引，每階段產物落對象存儲、按內容 hash 冪等，失敗入死信可重跑。解析按文件類型分流：有文字層嘅 PDF 用版面分析保留閱讀順序同標題層級；掃描件走 OCR；表格單獨抽成結構化（HTML/Markdown，保留表頭），大表按行切並每塊重複表頭；圖片/圖表可以用多模態模型生成描述。清洗去頁眉頁腳、斷行連字。每個 chunk 帶 doc_id、頁碼、章節路徑、版本，方便引用同刪除。質量上用抽樣人工檢查 + 檢索 eval 回歸，因為解析器升級會改變所有下游 chunk。

## 關鍵設計點
- **類型偵測**：唔好信副檔名，睇 MIME/magic bytes；PDF 再判斷有冇文字層（抽到嘅字符數/頁太少 → 當掃描件走 OCR）。
- **PDF 坑**：
  - 多欄排版：直接抽文字會左右串行 → 用 layout 分析（按區塊座標排閱讀順序）。
  - 頁眉頁腳/頁碼：跨頁重複 → 統計每頁相同位置重複文本去除。
  - 斷字連字（hyphenation）、換行唔等於分段 → 合併。
  - 標題層級：用字體大小/粗體推斷，做成章節路徑（`第3章 > 3.2 費率`），寫入 chunk metadata 同 chunk 開頭，提升檢索。
- **表格**：最常見失分位。抽成 Markdown/HTML 保留行列；大表按行分塊，**每塊重複表頭**，否則「0.1%」唔知係咩欄；合併儲存格要展開；數字題考慮直接存入 SQL 表俾 text-to-SQL/工具查，唔一定 embedding。
- **OCR**：掃描件、圖片；要記錄置信度，低置信度頁標記人工複核；中英混排、繁簡要揀合適模型；OCR 好貴好慢 → 獨立隊列同配額。
- **多模態**：圖表/流程圖可以用 VLM 生成文字描述再 embedding，原圖連結放 metadata，回答時可引用頁碼。
- **管道工程**：
  - 每階段產物（raw → parsed JSON → chunks）落 S3，方便換 embedding 模型時唔使重新解析。
  - 冪等鍵：`doc_hash + parser_version + chunker_version`；內容冇變就跳過。
  - 大文件分頁並行解析，再按頁序合併。
  - 失敗分類：加密 PDF、損壞文件、超大文件 → 死信 + 通知上傳方，唔好靜默吞咗。
  - 安全：解析器處理不可信文件（zip bomb、惡意 PDF）→ 沙箱、大小/頁數上限、超時。文件入面隱藏文字（白字、極細字）可能係 prompt injection，要偵測或者標記。
- **版本與刪除**：文檔更新 → 舊 chunks 按 doc_id 整批刪再寫新版（或者帶 version 原子切換），避免新舊混雜；權限 metadata（ACL）跟 chunk 走。
- **質檢**：每次升級解析器跑一套固定樣本文件 diff 輸出 + 檢索 eval（Recall@k）回歸；線上抽樣檢查「被引用 chunk 讀唔讀得明」。

## 常見追問（連答案）
**Q1：點樣知道係解析問題定檢索問題？**
答：拎失敗 case 去睇正確答案所在嘅 chunk 原文：如果 chunk 本身已經亂（表頭冇咗、文字串行、OCR 錯字），係解析問題；如果 chunk 乾淨但冇被檢索出嚟，係 embedding/檢索問題；如果檢索到但答錯，係生成問題。按管道階段逐段定位，同查後端鏈路一樣。

**Q2：表格數據問「A 方案 VIP3 費率幾多」，RAG 成日答錯，點改？**
答：一，解析時保留表格結構，每塊帶表頭同表名；二，chunk 唔好切斷行；三，數值精確查詢考慮將表入結構化存儲，用工具/SQL 查，LLM 只負責理解問題同組織答案；四，加呢類問題入 eval 集回歸。

**Q3：換咗更好嘅解析器，上線要注意咩？**
答：解析器變 → 所有 chunk 變 → embedding 全部重算，等同一次 reindex：用新 version 建新索引，replay/shadow eval 對比 Recall 同答案質量，再藍綠切換別名，舊索引保留可回滾。因為有中間產物落 S3，只需重跑解析之後嘅階段。

**Q4：用戶上傳 500 頁 PDF，點樣唔拖慢系統？**
答：上傳即返回 job id，異步處理；按頁拆分並行解析；OCR 走獨立低優先隊列；進度可查（已處理頁數）；設頁數/大小上限同租戶配額，防止一個租戶佔滿 worker。

**Q5：文件裏有隱藏指令（白色細字「忽略之前指示」）點防？**
答：解析時偵測異常樣式文字（顏色同背景相近、字號極細、不可見層）並剔除或標記；chunk 喺 prompt 入面當數據區塊，唔當指令；高權限動作唔可以由檢索內容觸發（同 prompt injection 防線一致）。

## 小練習（附參考答案）
**題目：** 合規部要將 2 萬份 PDF（一半係掃描件，好多費率表、兩欄排版）接入內部 RAG 問答。請設計 ingestion 管道，並講你點驗收。

**參考答案：**
1. **流程**：上傳 S3 → 事件入 MQ → 類型偵測（magic bytes + 文字層判斷）→ 分流：文字 PDF 走 layout 解析；掃描件走 OCR 隊列（獨立 worker、記錄每頁置信度）→ 表格抽成 Markdown 保留表頭 → 清洗（頁眉頁腳、斷字）→ 按章節結構切塊，大表按行切並重複表頭 → 帶 metadata（doc_id、頁碼、章節路徑、版本、ACL）→ embedding → 寫索引。
2. **工程保障**：每階段產物落 S3；冪等鍵 `doc_hash + parser_version`；加密/損壞文件入死信並出報告；解析跑沙箱 + 頁數/時間上限；按頁並行、OCR 限流。
3. **驗收**：(a) 抽 100 份分層樣本（文字/掃描/表格多/兩欄）人工檢查解析輸出閱讀順序、表頭完整、OCR 錯字率；(b) 合規同事出 200 條真實問題（包括費率表精確數字題）建 eval 集，量 Recall@5 同答案準確率；(c) 低 OCR 置信度頁清單交人工複核；(d) 費率類精確查詢如果準確率唔達標，改走結構化表 + 工具查詢。
4. **加分**：解析器版本升級要跑同一套樣本 diff + 檢索回歸，藍綠切索引。
